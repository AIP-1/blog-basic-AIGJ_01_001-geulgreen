요즘 웹 화면을 만든다고 하면 대부분 리액트나 뷰 같은 프레임워크부터 떠올려요. 저도 그랬어요. 그런데 최근에 작은 사내 도구를 만들면서 스프링과 타임리프로만 화면을 구성해 봤는데, 생각보다 훨씬 편하고 빨라서 놀랐어요. 오늘은 그 경험을 바탕으로 서버 렌더링을 다시 한번 살펴보려고 해요.

## 왜 다시 서버 렌더링일까

### 화면이 단순하면 도구도 단순해야 해요

제가 만든 도구는 목록을 보여 주고, 항목을 추가하고, 수정하는 정도가 전부였어요. 이런 화면에 번들러, 상태 관리 라이브러리, 라우터까지 붙이니 배보다 배꼽이 더 커지더라고요. 빌드 설정을 맞추는 데만 반나절이 걸렸어요.

그래서 과감하게 방향을 바꿨어요. 서버가 완성된 HTML을 만들어서 내려주고, 브라우저는 그걸 그대로 보여 주기만 하는 방식이요. 이게 바로 서버 렌더링이에요.

### 생각보다 많은 장점

직접 써 보면서 느낀 장점을 정리해 보면 이래요.

- 첫 화면이 빨리 떠요. 자바스크립트를 내려받고 실행할 때까지 기다릴 필요가 없어요.
- 검색 엔진이 내용을 바로 읽을 수 있어요.
- 화면 상태를 서버 한 곳에서만 관리하니 버그가 줄어요.
- 자바스크립트가 꺼진 환경에서도 기본 기능이 동작해요.
- 배포할 때 프론트엔드와 백엔드를 따로 맞출 필요가 없어요.

> 모든 화면이 앱처럼 동작할 필요는 없어요. 문서처럼 보이는 화면은 문서처럼 만드는 게 자연스러워요.

## 타임리프로 화면 만들기

### 기본 구조

타임리프는 HTML 파일에 특별한 속성을 붙여서 서버 데이터를 끼워 넣는 방식이에요. 템플릿 파일 자체가 브라우저에서 그냥 열어도 깨지지 않는다는 게 큰 장점이에요. 디자이너와 협업할 때도 편해요.

컨트롤러에서는 화면에 필요한 데이터를 모델에 담고, 템플릿 이름을 돌려주면 끝이에요. 아래는 제가 실제로 쓴 코드를 조금 단순하게 바꾼 거예요.

```java
@Controller
@RequiredArgsConstructor
public class TaskController {

    private final TaskService taskService;

    @GetMapping("/tasks")
    public String list(Model model) {
        model.addAttribute("tasks", taskService.findAll());
        return "tasks/list";
    }

    @PostMapping("/tasks")
    public String create(@Valid TaskForm form, BindingResult result) {
        if (result.hasErrors()) {
            return "tasks/new";
        }
        taskService.create(form);
        return "redirect:/tasks";
    }
}
```

### 폼 처리가 정말 편해요

서버 렌더링에서 제일 편했던 부분은 폼 처리였어요. 입력값 검증에 실패하면 같은 화면을 다시 보여 주면서 에러 메시지를 붙여 주면 돼요. 자바스크립트로 따로 검증 로직을 짜고, 서버 검증과 맞추고, 에러 상태를 관리할 필요가 없어요.

그리고 저장에 성공하면 리다이렉트를 해요. 이렇게 하면 사용자가 새로고침을 눌러도 같은 요청이 두 번 들어가지 않아요. 이 패턴을 "POST 다음 리다이렉트 다음 GET"이라고 부르는데, 오래됐지만 여전히 아주 쓸모 있는 방법이에요.

### 공통 레이아웃 나누기

헤더나 푸터처럼 모든 화면에 들어가는 부분은 조각으로 따로 빼 두고 불러와서 써요. 한 번 만들어 두면 화면이 늘어나도 관리가 쉬워요. 메뉴 하나를 바꿀 때 파일 하나만 고치면 되니까요.

## 그래도 자바스크립트가 필요한 순간

### 조금씩만 얹어요

서버 렌더링을 한다고 해서 자바스크립트를 아예 안 쓰는 건 아니에요. 다만 꼭 필요한 곳에만 조금씩 얹는 방식으로 접근해요. 예를 들면 삭제 버튼을 누를 때 확인 창을 띄우거나, 글자 수를 실시간으로 세어 주는 정도요.

```javascript
document.querySelectorAll('[data-confirm]').forEach((button) => {
  button.addEventListener('click', (event) => {
    if (!window.confirm(button.dataset.confirm)) {
      event.preventDefault();
    }
  });
});
```

이렇게 하면 자바스크립트가 동작하지 않아도 기본 기능은 그대로 살아 있고, 동작할 때만 더 편해져요. 이걸 점진적 향상이라고 불러요.

### 이런 경우엔 프레임워크가 나아요

물론 모든 상황에 서버 렌더링이 맞는 건 아니에요. 화면 안에서 상태가 복잡하게 얽히는 경우라면 클라이언트 프레임워크가 훨씬 나아요. 실시간 협업 편집기나 드래그로 배치를 바꾸는 대시보드 같은 거요.

## 두 방식 비교해 보기

제가 느낀 차이를 표로 정리해 봤어요. 정답이 있는 건 아니고, 화면의 성격에 따라 고르면 된다고 생각해요.

| 항목 | 서버 렌더링 | 클라이언트 렌더링 |
| --- | --- | --- |
| 첫 화면 속도 | 빠름 | 번들 크기에 따라 다름 |
| 화면 전환 | 매번 새로 불러옴 | 부드러움 |
| 상태 관리 | 서버 한 곳 | 브라우저와 서버 양쪽 |
| 개발 준비 시간 | 짧음 | 상대적으로 김 |
| 잘 맞는 화면 | 목록, 상세, 폼 | 대시보드, 편집기 |

## 마무리하며

이번 경험으로 배운 건 "도구는 문제에 맞게 고르자"는 아주 기본적인 교훈이었어요. 익숙하다는 이유로 무거운 도구를 먼저 꺼내 들기보다, 화면이 정말 무엇을 해야 하는지부터 생각해 보는 습관을 들이고 싶어요.

혹시 작은 관리 화면이나 사내 도구를 만들 일이 있다면, 서버 렌더링으로 한번 시작해 보세요. 생각보다 빨리 끝나서 남는 시간에 커피 한 잔 여유 있게 마실 수 있을 거예요.
