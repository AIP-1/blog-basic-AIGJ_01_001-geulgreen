"도커만 쓰면 어디서든 똑같이 돌아간다"는 말을 철석같이 믿고 시작했어요. 결과부터 말하면, 똑같이 돌아가기까지 주말 이틀을 꼬박 썼어요. 이번 글은 제가 처음으로 도커를 이용해 서비스를 서버에 올리면서 겪은 삽질을 솔직하게 기록한 글이에요. 저처럼 처음 도커 배포를 해 보시는 분이라면 제가 밟은 지뢰를 피해 가실 수 있으면 좋겠어요.

## 시작하기 전의 상황

제가 배포하려던 건 백엔드 서버 하나, 프론트엔드 정적 파일, 그리고 데이터베이스였어요. 로컬에서는 각각 따로 실행하고 있었는데, 서버에 올리려니 설치할 게 너무 많았어요. 자바 버전도 맞춰야 하고, 노드 버전도 맞춰야 하고, 데이터베이스도 설치해야 하고요. 그래서 이참에 도커로 전부 묶어 보자고 마음먹었어요.

### 세운 목표

목표는 단순했어요.

- 서버에서는 도커만 설치되어 있으면 될 것
- 명령 하나로 전체 서비스를 띄울 수 있을 것
- 재시작해도 데이터가 사라지지 않을 것
- 설정값은 이미지에 굽지 않고 밖에서 주입할 것

지금 보면 하나하나가 다 함정이었어요.

## 첫 번째 삽질, 이미지가 너무 커요

처음 만든 도커파일은 이랬어요. 인터넷에서 본 예제를 대충 따라 했죠.

```text
FROM 큰 기본 이미지
소스 전체 복사
그 안에서 빌드
빌드 결과 실행
```

이렇게 만든 이미지 크기가 무려 1기가바이트를 넘었어요. 서버로 올리는 데만 한참 걸렸고, 소스를 한 줄만 고쳐도 처음부터 다시 빌드됐어요.

### 멀티 스테이지 빌드로 해결

해결책은 빌드하는 단계와 실행하는 단계를 나누는 거였어요. 빌드는 무거운 이미지에서 하고, 실행에는 결과물만 가벼운 이미지로 옮기는 방식이에요.

```bash
docker build -t myblog-backend:0.1 .
docker images myblog-backend
```

이렇게 바꾸고 나니 이미지 크기가 삼분의 일 이하로 줄었어요. 또 의존성을 내려받는 단계를 소스 복사보다 앞에 두니까, 소스만 바꿨을 때는 캐시 덕분에 빌드가 훨씬 빨라졌어요.

> 도커파일의 줄 순서는 곧 캐시 전략이에요. 자주 바뀌는 건 아래로, 잘 안 바뀌는 건 위로 두세요.

## 두 번째 삽질, 컨테이너끼리 서로를 못 찾아요

이미지를 다 만들고 컨테이너를 띄웠는데, 백엔드가 데이터베이스에 연결을 못 하고 계속 죽었어요. 로그를 보니 연결 거부 에러였어요.

### localhost의 함정

원인은 설정 파일에 데이터베이스 주소를 `localhost`로 적어 둔 거였어요. 로컬에서는 같은 컴퓨터니까 당연히 됐는데, 컨테이너 안에서 `localhost`는 그 컨테이너 자기 자신이에요. 데이터베이스는 다른 컨테이너에 있으니 찾을 수가 없었던 거죠.

컴포즈 파일로 서비스를 묶으면 같은 네트워크 안에서 서비스 이름으로 서로를 찾을 수 있어요. 그래서 주소를 서비스 이름으로 바꿨더니 바로 연결됐어요.

### 시작 순서 문제

그런데 이번엔 가끔씩만 연결이 실패했어요. 데이터베이스 컨테이너가 떴더라도 실제로 접속을 받을 준비가 되기 전에 백엔드가 먼저 연결을 시도했기 때문이에요. 컨테이너가 시작된 것과 서비스가 준비된 것은 다르다는 걸 이때 배웠어요. 상태 확인을 설정하고, 데이터베이스가 건강해진 뒤에 백엔드가 뜨도록 의존 조건을 걸어서 해결했어요.

## 세 번째 삽질, 데이터가 사라졌어요

이건 정말 식은땀이 났던 순간이에요. 테스트 삼아 글을 몇 개 써 놓고, 설정을 바꾸려고 컨테이너를 내렸다가 다시 올렸더니 글이 전부 없어져 있었어요.

### 볼륨을 몰랐던 대가

컨테이너는 기본적으로 지워지면 안의 데이터도 같이 사라져요. 데이터베이스 파일을 컨테이너 바깥에 보관하려면 볼륨을 연결해야 했어요. 이걸 모르고 운영 데이터를 넣었다면 정말 큰일 날 뻔했어요.

이 경험 이후로 정리한 원칙이에요.

1. 데이터베이스 데이터는 반드시 이름 있는 볼륨에 둬요.
2. 업로드 파일도 마찬가지로 볼륨에 둬요.
3. 컨테이너는 언제든 지워도 되는 존재라고 생각해요.
4. 볼륨은 주기적으로 백업해요.

## 네 번째 삽질, 설정과 비밀값

처음에는 데이터베이스 비밀번호를 설정 파일에 그대로 적어서 이미지에 함께 넣었어요. 그러다 문득, 이 이미지를 공개 저장소에 올리면 비밀번호도 같이 공개된다는 걸 깨달았어요.

### 환경 변수로 분리

설정값은 환경 변수로 받도록 바꾸고, 실제 값은 서버에만 있는 환경 파일에 넣었어요. 그리고 그 파일은 절대 저장소에 올라가지 않도록 무시 목록에 추가했어요. 예시 파일만 따로 만들어서 어떤 값이 필요한지만 알 수 있게 했고요.

정리하면 이런 식이에요.

| 구분 | 어디에 두나요 | 저장소에 올리나요 |
|---|---|---|
| 도커파일 | 프로젝트 루트 | 올려요 |
| 컴포즈 파일 | 프로젝트 루트 | 올려요 |
| 예시 환경 파일 | 프로젝트 루트 | 올려요 |
| 실제 환경 파일 | 서버에만 | 절대 안 올려요 |
| 데이터 볼륨 | 서버 디스크 | 안 올려요 |

## 다섯 번째 삽질, 시간과 로그

마지막으로 자잘한 문제들이 남아 있었어요.

- 컨테이너 시간대가 UTC라서 글 작성 시간이 이상하게 찍혔어요.
- 로그를 따로 설정하지 않았더니 디스크가 서서히 차올랐어요.
- 컨테이너가 죽어도 자동으로 다시 뜨지 않았어요.

### 하나씩 정리하기

시간대는 환경 변수로 지정했고, 로그는 파일 크기와 개수에 제한을 걸었어요. 재시작 정책도 추가해서 서버가 재부팅되거나 컨테이너가 예기치 않게 종료돼도 다시 올라오게 했어요. 하나하나는 사소하지만, 이런 것들이 모여야 비로소 "운영할 수 있는" 상태가 되더라고요.

## 정리하며 배운 것

이틀간의 삽질을 표로 요약하면 이래요.

| 문제 | 원인 | 해결 |
|---|---|---|
| 이미지가 너무 큼 | 빌드 도구까지 포함 | 멀티 스테이지 빌드 |
| DB 연결 실패 | localhost 사용 | 서비스 이름으로 접근 |
| 간헐적 연결 실패 | 준비 전 접속 | 상태 확인과 의존 조건 |
| 데이터 소실 | 볼륨 미사용 | 이름 있는 볼륨 |
| 비밀값 노출 위험 | 이미지에 포함 | 환경 변수와 무시 목록 |
| 디스크 부족 | 로그 무제한 | 로그 크기 제한 |

돌이켜 보면 도커가 문제였던 적은 한 번도 없었어요. 늘 제가 컨테이너가 어떻게 동작하는지 제대로 이해하지 못한 게 문제였죠. 그래도 이렇게 한 번 크게 부딪히고 나니, 다음 프로젝트에서는 훨씬 수월하게 배포할 수 있을 것 같아요. 다음 글에서는 이 과정을 자동화해서, 코드를 올리면 알아서 배포되게 만든 이야기를 해 볼게요.
