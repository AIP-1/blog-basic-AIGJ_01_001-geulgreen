지난 몇 달 동안 퇴근 후 시간을 쪼개서 작은 블로그 서비스를 하나 만들었어요. 거창한 서비스는 아니고, 글을 쓰고 태그를 달고 댓글을 주고받을 수 있는 정도예요. 그런데 막상 만들어 보니 책이나 강의에서 보던 것과는 다른 고민이 정말 많았어요. 오늘은 그 과정에서 배운 것들을 차근차근 정리해 보려고 해요. 스프링 부트를 처음 써 보시는 분이나, 토이 프로젝트를 시작하려는 분께 조금이라도 도움이 되면 좋겠어요.

## 왜 스프링 부트를 골랐는지

처음에는 Node.js로 할지 스프링 부트로 할지 꽤 오래 고민했어요. 둘 다 장단점이 뚜렷하니까요. 결국 스프링 부트를 고른 이유는 생각보다 단순했어요.

- 회사에서 자바를 쓰고 있어서 익숙한 언어로 빠르게 시작하고 싶었어요.
- 인증, 트랜잭션, 검증 같은 기능이 이미 잘 정리되어 있어서 바퀴를 다시 만들 필요가 없었어요.
- 나중에 규모가 커져도 구조를 크게 바꾸지 않고 버틸 수 있을 거라는 믿음이 있었어요.

물론 단점도 있었어요. 처음 프로젝트를 띄울 때 설정할 게 은근히 많고, 어노테이션 하나가 뒤에서 무슨 일을 하는지 모르면 디버깅이 막막해져요. 그래도 한 번 흐름을 이해하고 나니 오히려 그 "보이지 않는 마법"이 개발 속도를 많이 올려 줬어요.

### 처음 세운 원칙

시작하기 전에 스스로 몇 가지 원칙을 정했어요. 토이 프로젝트일수록 끝까지 가기가 어렵다는 걸 경험으로 알고 있었거든요.

1. 기능은 작게, 대신 끝까지 동작하게 만들기
2. 테스트 없이 머지하지 않기
3. 설정값은 코드에 박지 않고 환경 변수로 빼기
4. 한 번에 하나의 기능만 브랜치에서 작업하기

이 네 가지만 지켜도 프로젝트가 덜 흔들렸어요. 특히 첫 번째 원칙 덕분에 "언젠가 완성할 거대한 기능" 대신 "오늘 끝낼 수 있는 작은 기능"에 집중할 수 있었어요.

## 계층 구조는 단순하게

스프링 부트 프로젝트를 시작하면 대부분 컨트롤러, 서비스, 리포지토리로 나누는 구조를 쓰게 돼요. 저도 그렇게 했는데, 처음에는 너무 잘게 나누려다가 오히려 길을 잃었어요. 인터페이스를 만들고, 구현체를 만들고, 매퍼를 만들고, DTO를 세 종류씩 만들다 보니 글 하나 저장하는 데 파일을 일곱 개나 열어야 했어요.

결국 다음처럼 정리했어요.

| 계층 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 컨트롤러 | 요청을 받고 응답 형식을 맞춰요 | 비즈니스 규칙을 판단하지 않아요 |
| 서비스 | 규칙을 검사하고 트랜잭션을 묶어요 | HTTP를 알지 않아요 |
| 리포지토리 | 데이터를 읽고 써요 | 권한을 따지지 않아요 |
| 엔티티 | 상태와 간단한 규칙을 가져요 | 다른 엔티티를 직접 저장하지 않아요 |

"하지 않는 일" 칸을 따로 적어 둔 게 의외로 큰 도움이 됐어요. 코드를 짜다가 애매할 때 이 표를 보면 어디에 넣어야 할지 금방 판단이 섰거든요.

### 서비스 메서드 하나의 모습

실제로 글을 저장하는 서비스 메서드는 이 정도 크기로 유지하려고 했어요.

```java
@Transactional
public PostResponse create(Long authorId, PostRequest request) {
    User author = userRepository.findById(authorId)
            .orElseThrow(() -> new NotFoundException("사용자를 찾을 수 없어요"));

    Post post = Post.write(author, request.title(), request.body());
    post.replaceTags(tagService.findOrCreate(request.tags()));

    return PostResponse.from(postRepository.save(post));
}
```

메서드가 한눈에 들어오는 크기를 넘어가면, 그건 보통 엔티티로 옮길 규칙이 섞여 있다는 신호였어요. 예를 들어 "제목은 비어 있으면 안 된다" 같은 규칙은 `Post.write` 안으로 들어가는 게 더 자연스러웠어요.

## JPA와 친해지기까지

솔직히 이 프로젝트에서 가장 많이 헤맨 부분이 JPA였어요. 처음에는 편하다고 생각했는데, 글 목록 페이지를 만들고 나서 로그를 켜 보고 깜짝 놀랐어요. 글 스무 개를 불러오는데 쿼리가 마흔 개 넘게 나가고 있었거든요.

### N+1 문제를 직접 만나다

원인은 흔히 말하는 N+1 문제였어요. 글을 가져온 다음, 글마다 작성자와 태그를 따로 조회하고 있었던 거예요. 이걸 해결하면서 배운 걸 정리하면 이래요.

- 목록 화면에서는 필요한 연관만 페치 조인이나 엔티티 그래프로 한 번에 가져와요.
- 컬렉션을 페치 조인하면서 페이징을 걸면 메모리에서 잘리니까 조심해야 해요.
- 그럴 때는 배치 사이즈 설정으로 연관 조회를 묶어 주는 게 훨씬 안전했어요.

> 쿼리 로그를 켜 두지 않은 JPA는 눈을 감고 운전하는 것과 같다는 말을, 이번에 몸으로 이해했어요.

이후로는 개발 환경에서 항상 SQL 로그를 켜 두고, 새 화면을 만들 때마다 쿼리 수를 세어 보는 습관이 생겼어요.

### 지연 로딩과 트랜잭션 경계

또 하나 자주 만난 에러가 지연 로딩 관련 예외였어요. 트랜잭션이 끝난 뒤에 연관 객체에 접근하면 터지는 그 에러요. 처음에는 설정으로 우회하고 싶은 유혹이 컸는데, 결국 응답 DTO를 서비스 안에서 만들어서 넘기는 방식으로 정리했어요. 컨트롤러는 엔티티를 아예 모르게 하니까 오히려 구조가 깔끔해졌어요.

## 테스트가 나를 살렸던 순간들

처음에는 테스트를 쓰는 게 귀찮았어요. 기능 하나 만드는 시간보다 테스트 짜는 시간이 더 걸릴 때도 있었으니까요. 그런데 프로젝트 중반에 태그 저장 방식을 통째로 바꿀 일이 생겼고, 그때 테스트가 없었다면 아마 포기했을 거예요.

### 어떤 테스트를 얼마나

모든 걸 테스트하려고 하진 않았어요. 대신 이런 기준을 세웠어요.

| 대상 | 테스트 방식 | 이유 |
|---|---|---|
| 엔티티 규칙 | 순수 단위 테스트 | 빠르고 스프링이 필요 없어요 |
| 서비스 흐름 | 통합 테스트 | 트랜잭션과 쿼리까지 확인해요 |
| 컨트롤러 | 웹 계층 슬라이스 테스트 | 요청과 응답 형식만 확인해요 |

테스트를 돌리는 명령은 늘 같았어요. 커밋 전에 습관처럼 한 번씩 돌렸어요.

```bash
./gradlew test --tests "*PostServiceTest"
./gradlew build
```

빌드가 초록색으로 끝나는 걸 보는 게 생각보다 큰 안심이 됐어요. 특히 밤늦게 작업하다가 실수를 했을 때, 다음 날 아침 테스트가 먼저 알려 주는 경험을 몇 번 하고 나니 테스트를 귀찮아하던 마음이 많이 사라졌어요.

## 배포하면서 깨달은 것들

로컬에서 잘 돌아가던 서비스가 서버에 올라가자마자 이상하게 동작하는 경험, 다들 한 번쯤 있으시죠. 저도 예외는 아니었어요.

- 로컬은 시간대가 한국인데 서버는 UTC여서 글 작성 시간이 아홉 시간씩 어긋났어요.
- 업로드 파일 경로를 상대 경로로 써서 재시작할 때마다 파일이 사라졌어요.
- 데이터베이스 스키마를 자동 생성 옵션에 맡겼다가 컬럼 하나가 의도치 않게 바뀌었어요.

마지막 문제 이후로는 마이그레이션 도구를 도입해서, 스키마 변경은 반드시 버전이 붙은 SQL 파일로만 하도록 바꿨어요. 처음에는 번거로웠지만, 어떤 변경이 언제 들어갔는지 기록이 남으니까 마음이 훨씬 편해졌어요.

## 다시 만든다면

마지막으로, 처음부터 다시 만든다면 바꾸고 싶은 점을 적어 볼게요.

1. 인증은 처음부터 제대로 설계할 거예요. 나중에 붙이려니 손댈 곳이 너무 많았어요.
2. 응답 형식과 에러 형식을 프로젝트 첫날 정해 둘 거예요.
3. 쿼리 로그와 테스트 환경을 기능보다 먼저 준비할 거예요.

돌아보면 기술 자체보다 "작게 만들고 자주 확인하는 습관"이 가장 큰 수확이었던 것 같아요. 스프링 부트는 그 습관을 들이기에 꽤 좋은 도구였고요. 다음 글에서는 검색 기능을 붙이면서 겪은 일을 정리해 볼게요. 읽어 주셔서 고마워요.
