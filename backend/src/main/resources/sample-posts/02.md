"쿼리가 느리면 인덱스를 걸면 된다"는 말, 한 번쯤 들어 보셨을 거예요. 반은 맞고 반은 틀린 말이에요. 인덱스는 분명 강력한 도구지만, 아무 데나 걸면 쓰기 성능이 떨어지고 저장 공간도 잡아먹어요. 이번 글에서는 PostgreSQL을 쓰면서 인덱스를 언제 걸고, 언제 과감히 빼야 하는지 제 경험을 바탕으로 정리해 볼게요.

## 인덱스가 하는 일 다시 보기

인덱스는 책 뒤쪽의 찾아보기와 비슷해요. 책 전체를 넘기지 않고도 원하는 단어가 몇 쪽에 있는지 바로 알 수 있게 해 주죠. 데이터베이스도 마찬가지로, 인덱스가 없으면 테이블을 처음부터 끝까지 읽어야 해요. 이걸 순차 스캔이라고 불러요.

### 공짜 점심은 없어요

그런데 찾아보기에도 비용이 있어요. 책에 새 내용이 추가되면 찾아보기도 고쳐야 하잖아요. 데이터베이스에서도 행을 넣거나 고치거나 지울 때마다 관련된 모든 인덱스를 함께 갱신해야 해요.

- 읽기는 빨라지지만 쓰기는 느려져요.
- 인덱스마다 디스크 공간을 따로 차지해요.
- 메모리에 올라가야 빠른데, 인덱스가 많으면 캐시를 서로 빼앗아요.
- 오래된 인덱스는 부풀어 오르기도 해서 주기적인 관리가 필요해요.

그래서 인덱스는 "많을수록 좋은 것"이 아니라 "필요한 만큼만 있어야 하는 것"이에요.

## 언제 인덱스를 걸어야 할까

제가 인덱스를 고민하는 기준은 대체로 이래요.

1. 자주 실행되는 쿼리의 조건절에 들어가는 컬럼인가요?
2. 그 조건으로 걸러지는 행이 전체에 비해 적은가요?
3. 정렬이나 조인에 반복해서 쓰이나요?
4. 고유해야 하는 값이라 제약 조건이 필요한가요?

이 질문에 "예"가 많을수록 인덱스를 걸 가치가 커져요.

### 선택도가 핵심이에요

특히 두 번째 질문이 중요해요. 예를 들어 회원 테이블에서 성별 컬럼처럼 값이 두세 개뿐인 컬럼은 인덱스를 걸어도 거의 쓸모가 없어요. 조건을 걸어도 절반쯤이 걸러지니까, 플래너 입장에서는 그냥 테이블을 다 읽는 게 더 싸거든요. 반대로 이메일처럼 거의 모든 값이 다른 컬럼은 인덱스 효과가 아주 커요.

### 복합 인덱스의 순서

여러 컬럼을 묶은 복합 인덱스를 만들 때는 순서가 정말 중요해요. 블로그 글 테이블을 예로 들어 볼게요.

```sql
-- 작성자별 최신 글 목록을 자주 조회한다면
CREATE INDEX idx_post_author_created
    ON post (author_id, created_at DESC);

-- 이 쿼리는 인덱스를 잘 활용해요
SELECT id, title
FROM post
WHERE author_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

이 인덱스는 `author_id`로 먼저 걸러 낸 뒤 `created_at` 순서대로 이미 정렬되어 있어서, 별도의 정렬 없이 앞에서 스무 개만 읽으면 끝나요. 하지만 `created_at`만으로 조회하는 쿼리에는 이 인덱스가 큰 도움이 안 돼요. 앞쪽 컬럼을 건너뛸 수 없으니까요.

## 실행 계획을 읽는 습관

인덱스를 걸었다고 끝이 아니에요. 정말 쓰이는지 확인해야 해요. 이때 가장 믿을 만한 도구가 실행 계획이에요.

> 추측하지 말고 측정하세요. 인덱스가 쓰일 거라는 믿음보다 실행 계획 한 줄이 더 정확해요.

실행 계획에서 제가 주로 보는 항목을 표로 정리해 봤어요.

| 항목 | 의미 | 눈여겨볼 점 |
|---|---|---|
| Seq Scan | 테이블 전체를 읽어요 | 큰 테이블에서 자주 보이면 의심해요 |
| Index Scan | 인덱스로 찾고 테이블을 읽어요 | 걸러지는 행이 적을 때 좋아요 |
| Index Only Scan | 인덱스만 읽고 끝나요 | 가장 빠른 경우가 많아요 |
| Bitmap Heap Scan | 여러 위치를 모아서 읽어요 | 중간 정도 선택도에서 자주 보여요 |
| rows 추정치 | 플래너가 예상한 행 수 | 실제 값과 크게 다르면 통계를 갱신해요 |

### 추정치가 틀릴 때

실행 계획에서 예상 행 수와 실제 행 수가 열 배, 백 배씩 차이 난다면 통계 정보가 오래된 경우가 많아요. 대량으로 데이터를 넣은 직후라면 통계를 한 번 갱신해 주는 것만으로도 플래너가 갑자기 똑똑해지는 걸 볼 수 있어요.

## 언제 인덱스를 빼야 할까

인덱스를 거는 것만큼 빼는 것도 중요해요. 시간이 지나면 처음에는 필요했던 인덱스가 쓸모없어지기도 하거든요.

### 쓰이지 않는 인덱스 찾기

PostgreSQL은 인덱스별로 몇 번이나 스캔되었는지 통계를 남겨 줘요. 이걸 보면 한 번도 안 쓰인 인덱스를 찾을 수 있어요. 다만 통계가 언제 초기화되었는지, 월말에만 도는 배치 쿼리가 있는지는 꼭 확인해야 해요. 한 달에 한 번 쓰이는 인덱스를 지웠다가 월말 정산이 멈추는 일은 겪고 싶지 않으니까요.

제가 인덱스를 지우기 전에 확인하는 목록이에요.

- 최근 충분한 기간 동안 스캔 횟수가 0인가요?
- 고유 제약이나 외래 키를 받치고 있는 인덱스는 아닌가요?
- 다른 복합 인덱스가 같은 역할을 이미 하고 있나요?
- 배치 작업이나 관리자 화면에서만 쓰이는 쿼리는 없나요?

### 중복 인덱스

의외로 자주 보이는 게 중복 인덱스예요. 예를 들어 `(author_id)` 인덱스와 `(author_id, created_at)` 인덱스가 함께 있다면, 앞의 것은 대부분 뒤의 것으로 대체할 수 있어요. 이런 인덱스를 정리하면 쓰기 성능이 눈에 띄게 좋아지기도 해요.

### 운영 중에 안전하게 다루기

운영 데이터베이스에서 인덱스를 만들거나 지울 때는 테이블 잠금을 조심해야 해요. 동시성 옵션을 쓰면 쓰기를 막지 않고 작업할 수 있어요. 대신 시간이 더 걸리고, 중간에 실패하면 유효하지 않은 인덱스가 남을 수 있으니 결과를 꼭 확인해야 해요.

```sql
CREATE INDEX CONCURRENTLY idx_comment_post
    ON comment (post_id);

DROP INDEX CONCURRENTLY IF EXISTS idx_post_author;
```

## 상황별로 정리해 보면

마지막으로 자주 만나는 상황을 묶어서 정리해 볼게요.

| 상황 | 추천 | 한 줄 이유 |
|---|---|---|
| 로그인용 이메일 조회 | 고유 인덱스 | 거의 모든 값이 달라요 |
| 상태값만으로 필터 | 보통 불필요 | 선택도가 낮아요 |
| 특정 상태만 자주 조회 | 부분 인덱스 | 필요한 행만 담아요 |
| 대소문자 무시 검색 | 표현식 인덱스 | 함수 결과에 인덱스를 걸어요 |
| 쓰기가 아주 많은 로그 테이블 | 최소한만 | 쓰기 비용이 커요 |

부분 인덱스는 특히 아껴 쓰기 좋은 기능이에요. 예를 들어 삭제되지 않은 글만 자주 조회한다면, 그 조건을 인덱스에 붙여서 크기를 확 줄일 수 있어요.

## 마치며

인덱스는 마법이 아니라 거래예요. 읽기 속도를 얻는 대신 쓰기 속도와 공간을 내주는 거죠. 그래서 정답은 늘 "우리 서비스의 쿼리가 어떻게 생겼는가"에 달려 있어요. 실행 계획을 읽고, 통계를 확인하고, 필요 없어진 인덱스는 미련 없이 정리하는 습관을 들이면 데이터베이스가 훨씬 건강해질 거예요. 다음에는 실행 계획을 한 줄씩 읽어 보는 글로 찾아올게요.
