서비스가 조금씩 커지면서 새로 합류한 팀원에게 구조를 설명할 일이 많아졌어요. 처음에는 말로 설명했는데, 듣는 사람도 저도 금방 헷갈리더라고요. 그래서 구조를 그림 세 장으로 정리해 보기로 했어요. 전체 구성, 사진 업로드 흐름, 배포 흐름이에요. 그림을 그리다 보니 제가 대충 알고 있던 부분이 어디인지도 드러나서, 저한테도 꽤 공부가 됐어요.

![브라우저에서 Spring Boot 앱을 거쳐 PostgreSQL, Redis, 사진 저장소로 이어지는 구조도와 브라우저에서 저장소로 바로 가는 업로드 화살표](image:16-1)

## 전체 구성 한눈에 보기

첫 번째 그림은 서비스 전체 구성도예요. 왼쪽에 브라우저가 있고, 가운데에 Spring Boot 앱이 있어요. 앱 오른쪽으로는 PostgreSQL, Redis, 사진 저장소가 나란히 붙어 있어요. 그리고 눈여겨볼 화살표가 하나 더 있는데, 브라우저에서 사진 저장소로 바로 가는 선이에요.

### 각 구성 요소의 역할

- 브라우저는 사용자가 글을 읽고 쓰는 화면이에요. 앱과는 주로 JSON으로 대화해요.
- Spring Boot 앱은 모든 판단을 맡아요. 로그인 확인, 권한 검사, 글 저장 같은 일을 해요.
- PostgreSQL은 글, 댓글, 사용자, 태그처럼 오래 남아야 하는 데이터를 저장해요.
- Redis는 자주 읽는 데이터를 잠깐 보관하는 캐시이자, 조회수처럼 빠르게 바뀌는 숫자를 세는 곳이에요.
- 사진 저장소는 사용자가 올린 이미지 파일을 보관해요.

정리하면 이렇게 볼 수 있어요.

| 구성 요소 | 맡은 일 | 잃어버리면 |
| --- | --- | --- |
| Spring Boot 앱 | 요청 처리와 판단 | 다시 띄우면 됨 |
| PostgreSQL | 영구 데이터 저장 | 복구가 꼭 필요함 |
| Redis | 캐시와 카운터 | 다시 채우면 됨 |
| 사진 저장소 | 이미지 파일 보관 | 복구가 꼭 필요함 |

"잃어버리면" 칸을 적어 보니 백업을 어디에 집중해야 하는지가 분명해졌어요. 앱과 Redis는 다시 만들 수 있지만, 데이터베이스와 사진은 사라지면 되돌릴 수 없어요.

### 사진은 왜 앱을 거치지 않을까요

처음 구조를 보는 분들이 가장 많이 묻는 게 브라우저에서 저장소로 바로 가는 화살표예요. 사진 파일은 크기가 커서, 앱이 중간에서 받아 다시 넘기면 앱의 메모리와 네트워크를 많이 써요. 그래서 앱은 "올려도 된다"는 허락만 해 주고, 실제 파일은 브라우저가 저장소에 직접 올리게 했어요. 앱은 가볍게 판단만 하고, 무거운 짐은 저장소가 받는 구조예요.

## 사진 업로드 흐름

두 번째 그림은 사진 한 장이 올라가는 과정을 순서대로 그린 시퀀스 다이어그램이에요. 앞에서 말한 "직접 올리기"가 실제로 어떻게 돌아가는지 보여 줘요.

![승인 요청부터 공개 주소까지 이어지는 사진 업로드 시퀀스 다이어그램](image:16-2)

그림의 흐름을 단계별로 풀어 보면 이래요.

- 브라우저가 앱에 "사진을 올리고 싶어요" 하고 승인을 요청해요.
- 앱은 데이터베이스에 임시 사진 행을 하나 만들어요. 아직 완료되지 않은 상태예요.
- 앱이 저장소에 올릴 수 있는 업로드 주소를 만들어 브라우저에 돌려줘요.
- 브라우저가 그 주소로 원본과 썸네일을 각각 PUT으로 올려요.
- 업로드가 끝나면 브라우저가 앱에 완료 알림을 보내요.
- 앱은 저장소에 올라간 파일의 크기와 형식을 검사해요.
- 검사를 통과하면 임시 행을 완료로 표시해요.
- 마지막으로 앱이 공개 주소를 브라우저에 알려 주고, 글에 사진이 붙어요.

### 검사를 앱이 다시 하는 이유

브라우저에서도 파일 크기를 확인하지만, 그건 사용자 편의를 위한 거예요. 브라우저 쪽 검사는 얼마든지 우회할 수 있어서, 최종 판단은 반드시 앱이 해야 해요. 그래서 완료 알림을 받으면 앱이 저장소에 직접 물어서 크기와 형식을 다시 확인해요. 검사에 실패하면 파일을 지우고 임시 행도 정리해요.

> 사용자가 보낸 값은 언제나 "주장"일 뿐이에요. 서버가 직접 확인한 것만 "사실"로 받아들여요.

### 임시 행은 왜 필요할까요

업로드 도중에 사용자가 창을 닫아 버리면, 저장소에는 파일이 반쯤 올라간 채 남을 수 있어요. 임시 행이 있으면 "시작은 했는데 완료되지 않은 사진"을 찾을 수 있어요. 하루 한 번 이런 행을 모아서 파일과 함께 지우는 정리 작업을 돌리고 있어요.

## 배포 흐름

세 번째 그림은 코드가 서버에 올라가기까지의 배포 흐름이에요. 이 그림에서 가장 중요한 건 실패했을 때 되돌아가는 화살표예요.

![PR 합치기부터 상태 확인까지의 배포 흐름과 실패 시 되돌리기 화살표](image:16-3)

흐름은 왼쪽에서 오른쪽으로 이어져요. PR을 합치면 테스트가 돌고, 통과하면 이미지를 빌드해요. 그다음 서버에 접속해서 새 버전을 실행하고, 마지막으로 상태 확인을 해요. 상태 확인에서 문제가 생기면 이전 버전으로 되돌려요.

### 배포 스크립트의 핵심 부분

실제 배포 스크립트에서 상태 확인과 되돌리기 부분만 간단히 옮겨 보면 이래요.

```bash
NEW_TAG="$1"
OLD_TAG="$(cat current_tag)"

docker run -d --name blog-new "blog:${NEW_TAG}"

for i in 1 2 3 4 5; do
  if curl -fs http://127.0.0.1:8080/actuator/health > /dev/null; then
    echo "새 버전 정상"
    echo "${NEW_TAG}" > current_tag
    exit 0
  fi
  sleep 5
done

echo "상태 확인 실패, 이전 버전으로 되돌려요"
docker rm -f blog-new
docker run -d --name blog "blog:${OLD_TAG}"
exit 1
```

다섯 번 정도 기다려 보고 그래도 응답이 없으면 바로 이전 버전으로 돌아가요. 사람이 밤새 지켜보지 않아도 서비스가 멈춘 채로 오래 남지 않게 하려는 장치예요.

### 되돌리기를 미리 연습해요

되돌리기 기능은 막상 필요할 때 안 되면 소용이 없어요. 그래서 한 달에 한 번은 일부러 실패하는 버전을 올려서 되돌리기가 제대로 되는지 확인해요. 처음 연습했을 때 이전 버전 번호를 저장하는 파일이 비어 있어서 되돌리기가 실패한 적이 있었어요. 실제 장애 때 이걸 알았으면 정말 아찔했을 거예요.

## 그림으로 정리하며 배운 것

세 장의 그림을 그리면서 몇 가지를 느꼈어요.

- 그림을 그리려면 화살표 하나하나의 방향을 정해야 해서, 애매하게 알던 부분이 바로 드러나요.
- 한 그림에는 한 가지 질문만 담는 게 좋아요. "무엇이 있나", "어떤 순서인가", "어떻게 배포하나"처럼요.
- 실패했을 때의 경로를 꼭 그려 둬요. 성공 경로만 그린 그림은 절반짜리예요.
- 그림은 코드가 바뀔 때 같이 고쳐야 해요. 오래된 그림은 없는 것보다 더 혼란스러워요.

새로 온 팀원은 이 세 장을 보고 반나절 만에 전체 구조를 이해했다고 했어요. 말로 설명할 때보다 훨씬 빨랐어요. 다음에는 알림이 전달되는 흐름도 그림으로 정리해 볼 생각이에요. 여러분도 팀의 서비스 구조를 한 장으로 그려 보세요. 그리는 과정 자체가 가장 좋은 복습이 될 거예요.
