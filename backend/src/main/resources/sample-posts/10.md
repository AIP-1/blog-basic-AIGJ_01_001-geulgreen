서비스가 조금씩 느려지기 시작하면 가장 먼저 나오는 말이 "레디스 붙이면 되지 않아요?"예요. 저도 예전에 그렇게 말했던 사람이에요. 그런데 실제로 캐시를 도입하고 운영해 보니, 붙이는 건 쉬워도 잘 쓰는 건 정말 어렵다는 걸 알게 됐어요. 오늘은 레디스 캐시를 도입하기 전에 팀에서 꼭 이야기해 봤으면 하는 것들을 정리해 보려고 해요.

## 정말 캐시가 필요한지부터

### 느린 이유를 먼저 찾아요

캐시는 느린 걸 빠르게 만드는 마법이 아니라, 같은 일을 반복하지 않게 해 주는 도구예요. 그래서 먼저 왜 느린지를 정확히 알아야 해요. 제가 겪었던 경우를 보면 생각보다 많은 문제가 캐시 없이 해결됐어요.

- 인덱스가 빠져 있어서 전체 테이블을 훑고 있었던 경우
- 목록 하나를 그리려고 쿼리를 수십 번 날리던 경우
- 필요 없는 컬럼까지 전부 불러오던 경우
- 외부 API 응답을 기다리느라 스레드가 묶여 있던 경우

이런 문제를 그대로 둔 채 캐시를 덮으면, 캐시가 비어 있는 순간마다 원래 문제가 다시 튀어나와요.

> 캐시는 문제를 숨길 수는 있어도 없애 주지는 않아요.

### 캐시가 잘 맞는 데이터

반대로 캐시가 정말 빛나는 경우도 있어요. 자주 읽히고, 잘 바뀌지 않고, 조금 오래된 값을 보여 줘도 괜찮은 데이터예요. 인기 글 목록, 설정값, 카테고리 목록 같은 것들이 대표적이에요.

## 어떤 패턴으로 쓸지 정하기

### 가장 흔한 방식: 필요할 때 채우기

제일 많이 쓰는 방식은 먼저 캐시를 보고, 없으면 데이터베이스에서 읽어서 캐시에 넣는 방식이에요. 구조가 단순하고 이해하기 쉬워서 처음 도입할 때 추천해요.

```javascript
async function getPopularPosts(redis, db) {
  const key = 'posts:popular';
  const cached = await redis.get(key);
  if (cached) {
    return JSON.parse(cached);
  }

  const posts = await db.query('SELECT id, title FROM posts ORDER BY likes DESC LIMIT 10');
  await redis.set(key, JSON.stringify(posts), { EX: 60 });
  return posts;
}
```

### 쓰기와 함께 갱신하기

데이터를 저장할 때 캐시도 같이 고치는 방식도 있어요. 읽을 때 항상 최신 값을 볼 수 있다는 장점이 있지만, 저장 로직이 복잡해지고 실패했을 때 처리가 까다로워요. 저는 보통 갱신보다는 캐시를 지우는 쪽을 택해요. 다음 읽기에서 새로 채워지게요.

### 패턴 비교

| 패턴 | 장점 | 단점 | 잘 맞는 경우 |
| --- | --- | --- | --- |
| 필요할 때 채우기 | 단순하고 안전함 | 첫 요청은 느림 | 대부분의 조회 |
| 쓰기와 함께 갱신 | 항상 최신에 가까움 | 저장 로직이 복잡함 | 자주 읽고 가끔 쓰는 값 |
| 저장 시 캐시 삭제 | 구현이 쉬움 | 삭제 직후 몰림 가능 | 게시글 상세 같은 단건 |

## 만료 시간은 어떻게 정할까

### 정답은 없지만 기준은 있어요

만료 시간을 정할 때 저는 "이 값이 얼마나 오래됐으면 사용자가 불편할까"를 먼저 물어봐요. 인기 글 목록이 1분 늦게 바뀐다고 불평하는 사람은 거의 없어요. 하지만 재고 수량이 1분 늦으면 큰 문제가 될 수 있어요.

### 동시에 만료되는 문제

같은 시간에 만들어진 캐시가 같은 시간에 한꺼번에 사라지면, 그 순간 요청이 전부 데이터베이스로 몰려요. 그래서 만료 시간에 약간의 무작위 값을 더해 주는 게 좋아요. 예를 들어 60초에 0초에서 10초 사이 값을 더하는 식이에요. 작은 차이지만 효과가 꽤 커요.

## 운영하면서 꼭 챙길 것

### 키 이름 규칙

처음부터 키 이름 규칙을 정해 두지 않으면 나중에 어떤 키가 무엇인지 알 수 없게 돼요. 저희 팀은 이런 규칙을 썼어요.

```text
{서비스}:{대상}:{식별자}:{버전}
blog:post:1024:v2
blog:posts:popular:v1
blog:user:42:profile:v1
```

버전을 붙여 두면 저장 형식이 바뀌었을 때 버전만 올려서 예전 캐시를 자연스럽게 무시할 수 있어요.

### 레디스가 죽었을 때

가장 중요하지만 가장 자주 잊는 부분이에요. 레디스가 응답하지 않을 때 서비스 전체가 멈추면 안 돼요. 캐시는 어디까지나 보조 수단이니까, 연결에 실패하면 바로 데이터베이스에서 읽도록 처리해야 해요. 그리고 그 상황에서 데이터베이스가 버틸 수 있는지도 미리 확인해 두면 좋아요.

### 확인해 볼 지표

1. 캐시 적중률: 요청 중 몇 퍼센트가 캐시에서 해결되는지
2. 메모리 사용량: 한도에 가까워지면 어떤 키부터 지워지는지
3. 응답 시간: 캐시 도입 전후로 실제로 빨라졌는지
4. 데이터베이스 부하: 캐시가 비었을 때 얼마나 튀는지

## 마무리하며

레디스는 정말 좋은 도구예요. 하지만 좋은 도구일수록 언제 쓰지 말아야 할지도 알아야 해요. 캐시를 붙이기 전에 느린 원인을 먼저 찾고, 어떤 데이터를 얼마나 오래 둘지 정하고, 캐시가 없을 때의 상황까지 그려 보세요. 그 과정을 거치고 나면 캐시가 훨씬 든든한 동료가 되어 줄 거예요.
