팀에 새로 합류하면 가장 먼저 물어보게 되는 것 중 하나가 "브랜치는 어떻게 쓰세요?"예요. 같은 깃을 쓰더라도 팀마다 브랜치를 다루는 방식이 꽤 달라요. 이번 글에서는 가장 많이 비교되는 두 전략, Git Flow와 트렁크 기반 개발을 나란히 놓고 장단점을 살펴볼게요. 어느 쪽이 정답이라기보다, 우리 팀 상황에 어떤 게 맞는지 판단하는 데 도움이 되는 글이 되었으면 해요.

## 브랜치 전략이 왜 필요할까

혼자 개발할 때는 브랜치 전략이 크게 중요하지 않아요. 그냥 메인 브랜치에 커밋해도 아무 문제가 없죠. 그런데 사람이 둘, 셋으로 늘어나면 이야기가 달라져요.

- 서로의 작업이 충돌하지 않게 해야 해요.
- 아직 덜 된 기능이 배포되지 않게 해야 해요.
- 운영 중 급한 버그를 빠르게 고칠 수 있어야 해요.
- 어떤 버전에 어떤 변경이 들어갔는지 추적할 수 있어야 해요.

브랜치 전략은 이런 요구를 팀이 같은 방식으로 해결하기 위한 약속이에요. 약속이 없으면 각자 편한 대로 하게 되고, 결국 머지할 때마다 혼란이 생겨요.

## Git Flow 살펴보기

Git Flow는 역할이 정해진 여러 종류의 브랜치를 쓰는 전략이에요. 처음 보면 복잡해 보이지만, 각 브랜치의 역할을 이해하면 꽤 논리적이에요.

### 브랜치의 종류

| 브랜치 | 역할 | 수명 |
|---|---|---|
| main | 배포된 코드만 담아요 | 영구 |
| develop | 다음 배포를 준비하며 기능을 모아요 | 영구 |
| feature | 기능 하나를 개발해요 | 짧음 |
| release | 배포 전 마지막 점검을 해요 | 짧음 |
| hotfix | 운영 중 급한 버그를 고쳐요 | 아주 짧음 |

### 작업 흐름

기능 하나를 개발해서 배포하기까지의 흐름은 대략 이래요.

1. develop에서 feature 브랜치를 만들어요.
2. 기능을 다 만들면 develop으로 머지해요.
3. 배포할 때가 되면 develop에서 release 브랜치를 만들어요.
4. release에서 버그를 고치고 점검을 마치면 main과 develop 양쪽에 머지해요.
5. main에 버전 태그를 붙여요.

명령어로 보면 이런 느낌이에요.

```bash
git switch develop
git switch -c feature/comment-like
# 작업 후
git switch develop
git merge --no-ff feature/comment-like
git switch -c release/1.4.0
```

### Git Flow의 장점

Git Flow의 가장 큰 장점은 질서예요. 지금 운영 중인 코드가 무엇인지, 다음 배포에 무엇이 들어갈지가 브랜치만 봐도 명확해요. 배포 주기가 정해져 있고, 여러 버전을 동시에 관리해야 하는 제품에 특히 잘 맞아요. 예를 들어 설치형 소프트웨어나 앱처럼 사용자가 여러 버전을 쓰고 있는 경우요.

### Git Flow의 단점

반면 단점도 분명해요. 브랜치가 많다 보니 머지가 잦고, feature 브랜치가 오래 살아남으면 develop과 멀어져서 머지할 때 큰 충돌이 생기기 쉬워요. 또 release와 hotfix를 양쪽에 머지하는 걸 깜빡하면 수정 사항이 한쪽에서만 사라지는 일도 생겨요.

> 브랜치가 오래 살수록 머지는 아파져요. Git Flow의 고통 대부분은 여기서 와요.

## 트렁크 기반 개발 살펴보기

트렁크 기반 개발은 이름 그대로 하나의 줄기, 즉 메인 브랜치를 중심으로 모든 개발자가 자주 통합하는 방식이에요.

### 핵심 원칙

- 모두가 메인 브랜치에 하루에도 여러 번 통합해요.
- 브랜치를 만들더라도 수명은 하루 이틀 이내로 짧게 유지해요.
- 메인 브랜치는 언제나 배포 가능한 상태를 유지해요.
- 덜 된 기능은 브랜치가 아니라 기능 플래그로 숨겨요.

### 기능 플래그라는 도구

트렁크 기반 개발에서 가장 중요한 도구가 기능 플래그예요. 아직 완성되지 않은 기능도 메인에 합치되, 설정으로 꺼 두는 방식이에요. 이렇게 하면 코드는 계속 통합되면서도 사용자에게는 노출되지 않아요.

```java
if (featureFlags.isEnabled("comment-like")) {
    commentService.like(commentId, userId);
} else {
    throw new FeatureDisabledException("아직 준비 중인 기능이에요");
}
```

물론 플래그가 쌓이면 코드가 지저분해지니까, 기능이 완전히 열리면 플래그를 지우는 정리 작업을 꼭 해야 해요.

### 트렁크 기반 개발의 장점

가장 큰 장점은 통합의 고통이 작다는 거예요. 매일 조금씩 합치니까 충돌이 생겨도 작고, 금방 해결할 수 있어요. 또 메인이 항상 배포 가능한 상태라서 하루에도 여러 번 배포하는 팀에 잘 맞아요. 웹 서비스처럼 사용자가 항상 최신 버전만 쓰는 환경에서 특히 강력해요.

### 트렁크 기반 개발의 단점

대신 전제 조건이 까다로워요. 자동화된 테스트가 탄탄하지 않으면 메인이 금방 깨져요. 코드 리뷰도 빠르게 돌아가야 하고, 기능 플래그를 관리하는 습관도 필요해요. 팀원들이 작은 단위로 쪼개서 커밋하는 데 익숙하지 않으면 오히려 혼란이 커질 수 있어요.

## 한눈에 비교하기

두 전략을 나란히 놓고 보면 이래요.

| 기준 | Git Flow | 트렁크 기반 개발 |
|---|---|---|
| 브랜치 수 | 많아요 | 적어요 |
| 브랜치 수명 | 길 수 있어요 | 아주 짧아요 |
| 배포 주기 | 정기 배포에 유리해요 | 잦은 배포에 유리해요 |
| 미완성 기능 관리 | 브랜치로 격리해요 | 기능 플래그로 숨겨요 |
| 필요한 자동화 수준 | 보통 | 높음 |
| 여러 버전 동시 유지 | 쉬워요 | 어려워요 |

## 우리 팀에는 무엇이 맞을까

결국 선택은 팀 상황에 달려 있어요. 제가 판단할 때 던지는 질문들이에요.

### 스스로에게 던지는 질문

1. 우리는 얼마나 자주 배포하나요?
2. 사용자가 여러 버전을 동시에 쓰나요?
3. 자동화된 테스트를 얼마나 믿을 수 있나요?
4. 팀원들이 작은 단위로 작업을 쪼개는 데 익숙한가요?

배포가 한 달에 한 번이고 여러 버전을 유지해야 한다면 Git Flow가 편할 거예요. 반대로 하루에도 여러 번 배포하고 테스트가 탄탄하다면 트렁크 기반 개발이 훨씬 가볍게 느껴질 거예요.

### 중간 지점도 있어요

꼭 둘 중 하나만 골라야 하는 건 아니에요. 실제로 많은 팀이 메인 브랜치 하나에 짧은 기능 브랜치와 풀 리퀘스트를 쓰는 방식을 택해요. Git Flow의 복잡함은 덜고, 트렁크 기반 개발의 빠른 통합은 살리는 절충안이죠. 저희 팀도 처음에는 Git Flow로 시작했다가, 배포가 잦아지면서 점점 이쪽으로 옮겨 왔어요.

## 마치며

브랜치 전략은 도구라기보다 팀의 일하는 방식을 반영한 거울 같아요. 어떤 전략을 고르든, 팀원 모두가 같은 규칙을 이해하고 지키는 게 가장 중요해요. 그리고 상황이 바뀌면 전략도 바꿀 수 있다는 유연함을 잊지 않으셨으면 해요. 여러분 팀은 어떤 방식을 쓰고 계신가요? 댓글로 경험을 나눠 주시면 저도 많이 배울게요.
